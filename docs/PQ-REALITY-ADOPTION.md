# PQ-REALITY adoption policy

Status: **HOLD** as of 2026-07-10.

The canonical capability name is **VLESS Encryption (PQE) over REALITY**. This document uses **PQ-REALITY** only as an operator shorthand. VLESS PQE is an encryption layer inside VLESS; it is not the `X25519MLKEM768` key share used by browser-shaped uTLS profiles.

## Current decision

PQ-REALITY is not an operator-configurable feature in this repository. Every VLESS inbound whose `streamSettings.security` is `reality` must retain `settings.decryption: "none"`, and the changelog-driven guard in `XRAY-RELEASE-LINE.md` enforces that invariant through pre-commit, CI, and `make ci-fast`.

The HOLD decision has two independent causes. Xray tags that include VLESS PQE through `v26.6.27` remain Pre-release, while `v26.3.27` remains the GitHub-tagged Latest release. The supported client delivery path in this repository emits sing-box JSON and classical VLESS URIs, and sing-box does not support Xray's VLESS Encryption setting. Enabling only the server side would make the supported client artifacts incompatible.

HOLD means there is no PQE secret, schema field, Ansible variable, environment override, Make target, client field, or generated bundle field. Pre-release Xray builds may still be evaluated under the repository's general staging-only policy, but PQ-REALITY remains disabled in every environment until this policy moves to STAGING.

## Adoption phases

| Phase | Meaning | Required enforcement |
|---|---|---|
| **HOLD** | PQ-REALITY is unavailable in every environment. | Every REALITY inbound renders `settings.decryption: "none"`; no operator override or client claim exists. |
| **STAGING** | A future implementation may expose PQ-REALITY only to an isolated technical cohort. | The implementation PR must add server and client contracts together, keep production fail-closed, and replace rather than delete the HOLD guard. |
| **PRODUCTION** | PQ-REALITY may be offered to production cohorts after promotion evidence is complete. | The production gate must be machine-enforced and remain reversible without relying on undocumented operator steps. |

## Entry criteria for STAGING

All of the following must be satisfied in one reviewed implementation change:

- A repository-supported client path can express and validate the same VLESS Encryption contract as the server. Manual third-party client configuration is not sufficient.
- The matching server/client material can be generated by the pinned Xray binary, stored through the existing SOPS boundary, and emitted without exposing server-side secret material.
- The pinned Xray artifact and architecture checksums are recorded, upstream configuration documentation is unambiguous, and both server and supported client configurations pass their native validation commands.
- An explicit appearance-mode cohort is chosen from reproducible evidence and named only by its technical signature. No mode becomes a repository default from inference or anecdote.
- The schema, Ansible template, client generator, compatibility checks, rollback behavior, and tests land atomically. The production environment must reject the staging-only setting.

A Pre-release Xray tag may be used only after these criteria are met and only in STAGING. Pre-release status never satisfies the PRODUCTION phase.

## Promotion criteria for PRODUCTION

All of the following evidence is mandatory:

- The Xray tag carrying the tested PQE behavior is marked Latest and is not marked Pre-release upstream.
- The exact candidate configuration runs in STAGING for at least 48 continuous hours without configuration-validation, authenticated liveness, crash, or resource regressions.
- Authenticated data-plane liveness succeeds from at least two representative filtered sentinels using technical cohort labels; indeterminate or stale evidence fails closed.
- The previous binary and classical configuration are still available, and a rollback drill has restored authenticated liveness before promotion.
- Every affected client has a coordinated redistribution or migration path. Production promotion cannot strand a classical client or advertise PQE to a client that does not support it.

## Fail-closed transition rules

Missing evidence, unknown client compatibility, upstream schema ambiguity, unverified release status, failed validation, or incomplete rollback evidence leaves the phase at HOLD. An operator cannot change phase through SOPS, group variables, an environment variable, or a Make command.

Moving to STAGING or PRODUCTION requires an intentional reviewed repository change that updates this status, `XRAY-RELEASE-LINE.md`, the declarative guard, the server/client contracts, and their tests together. The HOLD guard must not be removed by itself; it must be replaced by an environment-aware guard that proves production remains disabled until every production criterion is satisfied.

If a staging or production trial fails, restore the prior Xray binary and classical configuration, verify authenticated REALITY liveness, and return this policy to HOLD before further investigation.

## Review evidence

Refresh the decision from primary upstream sources on every Xray release that mentions VLESS Encryption and every release of the supported client engine. The 2026-07-10 HOLD decision was checked against the [Xray release list](https://github.com/XTLS/Xray-core/releases), [Xray PR #5067](https://github.com/XTLS/Xray-core/pull/5067), and [sing-box issue #3599](https://github.com/SagerNet/sing-box/issues/3599).
