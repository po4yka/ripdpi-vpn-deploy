## Purpose

Provide observable, testable guarantees for deliver isolated reliable and upgradeable four-protocol connectivity across accepted inputs, successful operation, failure and retained authority.

## ADDED Requirements

### Requirement: REQ-PROTO-PORTFOLIO-ISOLATION — Safe complete baseline connectivity

The implementation MUST deliver positive P0 REALITY, P1 XHTTP and P2 Hysteria/AWG traffic while denying recipient-selected private destinations and binding each device to exact authorized server parameters.

#### Scenario: Baseline works

- **WHEN** all baseline child requirements and actual client cases complete on one exact source
- **THEN** public traffic works on every enabled surface and forbidden destinations/source identities receive no traffic

#### Scenario: Recipient or endpoint is invalid

- **WHEN** an ambiguous binding, invalid input, wrong credential or wrong TLS identity is selected
- **THEN** the corresponding path refuses before mutation while valid control clients retain service

### Requirement: REQ-PROTO-PORTFOLIO-LIFECYCLE — Reliable ownership and recovery

The implementation MUST preserve complete preceding runtime authority on failed activation and apply real daemon adoption, retirement, rotation and topology recovery without touching unrelated resources.

#### Scenario: A complete upgrade fails

- **WHEN** any candidate binary asset configuration TLS bind or readiness stage fails or is interrupted
- **THEN** old authenticated connectivity is restored or explicit private recovery debt remains and success is not claimed

#### Scenario: Owned state changes

- **WHEN** an instance, unit, runtime or profile changes and converges twice
- **THEN** actual running identity and traffic match desired state, removed owned paths stop, unrelated resources survive and unchanged convergence is idempotent

### Requirement: REQ-PROTO-PORTFOLIO-EVOLUTION — Eligible supported upgrade and feature adoption

The implementation MUST make stable candidate upgrades and typed optional endpoint/ECH features usable by supported real clients only after baseline security, acceptance, coordinated contracts and authenticated rollback pass.

#### Scenario: Candidate is eligible

- **WHEN** exact reviewed stable source/client versions complete native, physical where required, and separately authorized staging acceptance
- **THEN** selected supported clients complete actual traffic; optional features remain explicit and production promotion is a separate decision

#### Scenario: Candidate lacks support or eligibility

- **WHEN** a prerelease, unknown provenance, unconsumed server toggle, missing client evidence or unresolved rollback is offered
- **THEN** it cannot be accepted or promoted; a refusal-only state leaves the feature unfinished

### Requirement: REQ-PROTO-PORTFOLIO-EVIDENCE — Evidence belongs to its actual requirement and source

The implementation MUST keep all original findings traceable and acceptance credit scoped to exact source, runtime, target and evidence category without closing unfinished or cancelled work.

#### Scenario: Shared observations are recorded

- **WHEN** one complete exact-source run covers multiple child requirements
- **THEN** each named requirement maps to actual evidence and no old receipt is silently reassigned to a new contract

#### Scenario: A required layer is missing

- **WHEN** a selected native, physical, client or candidate-staging requirement is unexecuted or fails
- **THEN** the owner stays open with the exact unsatisfied check; planning or fixtures do not substitute and cancelled acceptance is not revived
