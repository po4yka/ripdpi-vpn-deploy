## Context

`contract/ripdpi-bundle.schema.json` is v2 and is checked by `scripts/validate-bundle.py` and `tests/unit/test_bundle_schema.py`. The generator `scripts/emit-bundle.sh` is changed by D4, not here.

## Goals / Non-Goals

- One canonical contract in this repository that RIPDPI R2 vendors byte-identically.
- Fixtures that prove each forbidden field is rejected.
- Non-goal: generator changes (D4), ingest (D2), client code (R2 to R4).

## Decisions

- Draft 2020-12 JSON Schema with `additionalProperties: false`, following the other files in `contract/`. Rejected: a looser schema validated by code, because the client must validate it offline.
- The histogram is an array of 8 counts aligned with the fixed bounds, so the bounds are not repeated per report. Assumption: counts are non-negative integers; the validator script, not the schema, checks that the histogram sum equals `attempts`. Recorded as an assumption for review.
- No bundle v2 compatibility: `schema_version` const 3. Rejected: oneOf v2 or v3, per owner policy.
- Assumption: `server_ref` pattern is `^[A-Za-z0-9_-]{1,64}$` and generated by D4 as an opaque id, not a hostname.
- Assumption: `cohort_token` is 22 to 64 characters of base64url; it is not a secret that identifies a device.
- Resolved during implementation: per-endpoint health lives in a new top-level `ripdpi.endpoints` map keyed by `server_ref` (the outbound or AWG tag), each entry `{health}`. The `ripdpi` object covers only AWG and Hysteria extras, so a field on those entries would leave VLESS and XHTTP without health. The validator refuses a key that names no tag of a full bundle. Bounds chosen: `ttl_seconds` 60 to 86400, `max_reports_per_day` 1 to 24, `buckets` 1 to 256, `attempts` and histogram counts at most 1000000, `asn` 1 to 4294967295; `observed_at` uses the `Z` suffix only.
- Resolved during implementation: the only in-repo producer constant, `schema_version` in `scripts/client_payload.py`, moves to 3 here so the emit-and-validate tests stay green. It emits no `endpoints` or `field_report`; D4 adds them. Fresh bundles must not be exported before RIPDPI R2 and R4 ship.
- Resolved during implementation: field-report negatives use the `report-` prefix in `contract/negative/` so the bundle negative glob `neg-*.json` does not pick them up. Field-report validation is `scripts/validate-field-report.py`, separate from `scripts/validate-bundle.py`, because the documents differ.

## Contracts and ownership

- `contract/client-field-report.schema.json` (new), `contract/ripdpi-bundle.schema.json`, fixtures, `scripts/validate-bundle.py`, `docs/reference/ripdpi-bundle.md`, `AGENTS.md` source-of-truth table.
- Serialized lane: this change is first; D4 changes `scripts/emit-bundle.sh` after it.

## Contract validation

- `scripts/validate-field-report.py` `validator()` is the one Draft 2020-12 checker for both contracts: `pattern` keeps the ECMA-262 end-of-input meaning of `$`, and `integer` admits only a JSON integer. `scripts/validate-bundle.py` loads it, and the ingest copies it. Clients must apply the same two rules to their vendored copies.

## Risks / Trade-offs

- Breaking v2 rejection strands old clients -> the break is named here and in D4; RIPDPI R2 and R4 ship before the generator emits v3.
- Schema too strict for the client taxonomy -> R2 vendors the schema and runs the golden fixtures.

## Migration Plan

Forward only. Land the schema and fixtures, then D4 emits v3. Rollback is a git revert of the schema together with the generator.
