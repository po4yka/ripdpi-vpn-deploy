## Context

Bundle v3 is generated by D4 and defined by D1. The schema, the validator, the emitter and the client copy must agree.

## Goals / Non-Goals

- Goal: Tell the client which transport entries can pass under an allowlist regime, without claiming that any address is permitted.
- Non-goal: any IP address, hostname, key or concrete evasion parameter in the repository.

## Decisions

- Decision 2026-11-26: amend bundle v3, no v4. Evidence: v3 generation is on main but has not been rolled to production (its verification record leaves live rollout to a separate operator decision), and the client v3 consumer is not in any RIPDPI release (latest release predates it). The label is an optional per-entry field with values yes/no/unknown, default unknown; values other than unknown are set only from field-report evidence, never by hand. Both repos must vendor the changed contract before either side ships v3. Step 1 implements the schema and validator change under this decision; it is not a new choice between amendment and bump.
- Field evidence for label values comes from the client allowlist verdict (po4yka/RIPDPI#DGN-1795704952088416); the client consumes the label (po4yka/RIPDPI#DAT-1795704964813672).
- Assumption: three values, not a score. A score would invite false precision from a single-source observation.
- Assumption: the class table is a small data file read by the emitter and by a test.

## Contracts and ownership

- `contract/`, `scripts/` bundle files, `docs/reference/ripdpi-bundle.md`. Serialized after D4. One writer.

## Risks / Trade-offs

- The observation may be wrong -> unknown is the default and yes is rare, so a wrong table entry costs attempts, not connectivity.
- Contract drift with the client -> the vendored copy check in `AGENTS.md` source of truth applies.

## Migration Plan

Forward only. Rollback reverts the change.
